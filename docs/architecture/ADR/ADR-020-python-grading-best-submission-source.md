# ADR-020：Python 批改以最高分正式提交为唯一事实源

- 日期：2026-11-09；2026-11-10 增补教师确认制
- 状态：最高分事实源与教师确认制均已上线（1.30.92）
- 关联：[需求](../../../contexts/python-grading/requirements.md)、[设计](../../../contexts/python-grading/design.md)、[1.30.88验收](../../../contexts/python-grading/release-1.30.88.md)、[1.30.90验收](../../../contexts/python-grading/release-1.30.90.md)

## 背景

Python 课程成绩保留历史最高分，判题明细保存在 `biz_programming_submission`，教师批改又把代码和分数混读 `biz_student_answer`。这会在无答题行、同分重交和并发提交时产生代码与判题指标错位，甚至让教师无法批改已经成功判题的作品。

## 备选方案

1. 继续以 `biz_student_answer` 为唯一来源：实现改动小，但无法覆盖异步提交和同分重交，不采用。
2. 每次重算全部历史答题行：能统一数据，但存在大批量写入和历史成绩风险，不采用。
3. 最高分正式提交作为判题事实，答题行作为课程成绩/任务状态写入点：读取和写入边界清晰，采用。

## 决策

- 最高分提交只接受正式 `SUBMIT`、非空分数和已知终态白名单。
- 排序固定为 `score DESC, judged_at DESC, submission_id DESC`；同分以新提交为准。
- 批改页代码、判题指标和下载代码来自同一提交。
- Python 写回答题表使用专用 upsert：高分保留，同分采用最新代码。
- 无答题行时可在批量采用事务内补建；人工评分也支持仅凭最高分提交建立可批改记录。
- 批量采用对答题行加锁，并复核当前最高分提交、退回状态和任务状态；1.30.90 起前端额外提交页面快照，后端逐人拒绝过期列表。
- 新增 `(student_id, lesson_id, question_id, submission_kind, score, judged_at, submission_id)` 索引。
- 2026-11-10 增补：系统判题分只作参考，学生提交不自动写 `biz_student_answer.score`；教师五星/数字评分或批量采用后才形成正式成绩。待批阶段同步最高分代码，教师评分后不为后续重交悄悄替换已评分版本。
- 教师运行查看按提交 ID 复用课程班级权限和隔离运行服务，不产生判题或成绩记录。

## 后果

- 正面：教师的代码、判题信息和最终分数保持同版本；异步/课后提交可正常批改；批量采用具备个案容错和并发保护。
- 约束：Python 与打字/理论题不能共用同一套答题行择优 SQL；后续修改必须保持 `upsertProgrammingAnswer` 与最高分查询同步。
- 数据：历史答题行未批量重算；只有新提交或教师批改触发写入。

## 验证与回退

后端业务全量 969 项通过、0 失败、3 跳过；Python 批量采用 4 项（含页面快照变更跳过）、前端批改刷新 12 项通过。130 线上 40/40 名有系统判题学生的最高分代码与数据库一致，`EXPLAIN` 命中新索引且无 filesort。

回退后端时新增索引可保留；已产生的正式答题行和成绩不回删。1.30.89 的窄屏布局只回退 Nginx 前端根；1.30.90 的页面快照保护回退时恢复该版本 service/nginx 备份并重启，更新 168 转 DRAFT。
