# ADR-001：先用县级 SIoT 2618 验证初中物联网链路

## 状态

已接受并实施；SIoT P1 已通过，但其独立强密码账号兼容失败，现进入标准 Broker 并行兼容复审。

## 背景

学生已经在 Mind+ 中编写掌控板 Wi-Fi、MQTT 和传感器程序。重新开发编程软件不现实；每校教师机临时启动 SIoT 又容易受本机防火墙、关机、IP 变化和课堂排错能力影响。当前首先要回答的是：学校掌控板能否稳定把数据发送到县平台可达的 MQTT 服务。

## 决策

保留县服务器 `10.52.1.123` 的 SIoT 2618 作为已验证的硬件回退路径；同时在扩展服务器 `10.52.1.129` 用 EMQX 5.8.8 进行并行兼容验证。EMQX 仅开放教育网至 `1883`，管理端仅本机回环，真实掌控板成功发布前不切换正式 Broker。

## 理由

- 不改变学生使用 Mind+ 的教学流程；
- 县服务器固定地址、自动启动和统一日志比教师机临时服务更稳定；
- 能快速把“硬件/学校网络问题”和“平台业务开发问题”分开验证；
- 独立目录、服务和端口，不影响 80/3005/3009/3010。

## 后果

- 当前共享默认账号仅用于 PoC，不能直接宣称具备多校租户隔离；
- 全县第一阶段继续使用 `10.52.1.123:1883`，通过 `county/{学校}/{课程}/{班级}/{实验}/{小组}/{设备}/data` Topic、平台权限和服务端映射隔离，不为教师、班级或实验创建新端口；
- EMQX 已具备强密码、设备级 Topic ACL 和默认拒绝策略，但 Mind+ 未实测通过前不作为正式路线。
- 真实掌控板 P1 已由用户现场确认通过，但连续运行、断网恢复和多校隔离仍需在 P2/试点阶段补充证据；
- P1 通过后才能开发平台接收器；P2 必须补设备令牌、Topic 授权、诊断事件和数据保留策略；
- 如果 SIoT 无法满足多校隔离、审计或稳定性要求，平台接收层保持 MQTT 标准协议不变，底层 Broker 可替换。

## 2026-08-19 进度补充
P2 平台代码、幂等 SQL、模拟器、后端测试和 Vue3 构建已完成；正式上线未完成。正式 SIoT 原始数据库备份已恢复，CountySIoTPoc 保持 Running。新增平台订阅账号的 MQTT 认证实际返回 CONNACK 5，因此未执行正式后端切换、正式库迁移或教师浏览器上线验收；该问题是当前上线阻断，需先按 SIoT 2618 的真实认证/Topic 管理方式解决。

## 产品落地补充（2026-08-19）

物联网不是独立于课程的后台工具，而是教师课程卡片上的一个课堂操作。课程卡片负责传入课程和权限范围，物联页负责实验、小组、设备配置及数据查看；学生仍在 Mind+ 使用平台生成的服务器、1883、账号、密码和 Topic。这样与现有课程、班级权限模型一致，也避免教师误以为新实验需要申请新 MQTT 端口。该入口已在本地 Vue3 实现并通过构建，正式发布仍受 SIoT 认证兼容阻断。
# 2026-08-20 补充：P2 Broker 决策

真实掌控板已验证 Mind+ 的 SIoT 模块可以连接 `10.52.1.129:1883` 的标准 EMQX。由于 SIoT 2618 无法可靠创建强密码独立账号，P2 正式平台采用 EMQX 的认证与 ACL 管理能力：每设备独立账号、精确 data Topic 发布权、平台独立订阅账号。原 SIoT `10.52.1.123` 不删除、不改配置，保留为回退链路。EMQX 管理 API 凭据仅注入平台后端环境，不能写入数据库、前端或文档。
