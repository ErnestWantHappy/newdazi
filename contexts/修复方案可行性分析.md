### BUG-14：评分去重失败

| 检查项 | 结果 |
|--------|------|
| 根因分析 | ✅ 正确。`IdentityHashMap` 只防同一对象引用重复，但同一 widget 经不同引用路径（如 `widgetList` 直接引用 vs `options` 嵌套引用）会产生不同的 Map 对象，绕过防重 |
| 现有兜底 | `deduplicateDetailList()` 已在 detail 层面做 fieldKey 去重（第 384-406 行），但审查报告指出仍出现重复，说明去重未完全生效 |
| 修复方案 | ⚠️ **方向正确，但实现有性能问题** |
| 性能问题 | 方案中 `result.stream().anyMatch(...)` 对每个 widget 做 O(n) 扫描，整体 O(n²)。对于 50+ 个 widget 的复杂表单，建议改用 `Set<String> addedKeys` 参数传递 |
| 修复建议 | 修改 `walkFlatten` 签名，增加 `Set<String> addedFieldKeys` 参数，用 O(1) 的 Set 操作替代 O(n) 的 stream 扫描 |

**改进后的方案：**

```java
private void walkFlatten(Object value, List<Map<String, Object>> result,
                         Set<Object> visited, Set<String> addedKeys) {
    // ... 现有逻辑 ...
    if (id != null && type != null && isRealWidget(map)) {
        String fieldKey = String.valueOf(id);
        if (addedKeys.add(fieldKey)) {  // O(1) 去重
            result.add(map);
        }
    }
    // ...
}
```

**结论：方案方向正确，但建议改用 Set 参数去重，避免 O(n²) 性能问题。**

## 五、P3 优化建议 — 逐项分析

- **注意**：需确保 `barChart`、`completionPie`、`accuracyPie` 三个变量在 `handleResize` 中可访问

- **可行性**：✅ 可行。检查 SecurityConfig 中的 CSRF 白名单配置

- **可行性**：✅ 完全可行。从 2000ms 改为 5000ms，降低 CPU 占用
- **风险**：⚠️ 极低。5 秒延迟对 HomeTab 注入兜底仍然足够

### OPT-07：预览页后端权限

### OPT-08：进度查询分页

- **注意**：前端看板每 5 秒轮询，分页后需确认前端能正确处理分页数据

### OPT-09：AI 评分线程池优雅关闭

- **风险**：⚠️ 中等。ALTER TABLE 修改字符集排序规则可能锁表，建议在维护窗口执行。也可先只移除 SQL 中的 COLLATE 子句，后续再统一数据库
