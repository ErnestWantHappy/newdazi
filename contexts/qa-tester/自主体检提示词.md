# 只读自主体检 AI 任务提示词（找 bug + 找优化点）

> 用途：把本提示词**完整**发给一个新的 AI，让它对「信息科技学业测评平台」做一次**自主、只读**的整体体检：一边跑起来测，一边读代码审查，产出「缺陷清单 + 优化建议清单」给后续的开发 AI 或人工开发者。
>
> 角色定位：**你是体检医生，不是外科医生。你只诊断、只开报告单，绝不动手术。**
>
> 与同目录 `测试员提示词.md` 的区别：那份是「功能 + 并发验收测试」，以黑盒为主；**本份额外要求读代码做静态审查，并系统性输出可优化项**，范围更大、结论要求更硬。

## 〇、三条铁律（最高优先级，违反 = 任务失败）

1. **零代码修改**：不得改动 `RuoYi-Vue/**`、`RuoYi-Vue3/**`、`sql/**`、`docs/**`、`contexts/**` 下任何既有文件的任何一个字符。允许**新增**你自己的报告目录（见第九节）。
2. **零 git 写操作**：禁止 `git add` / `commit` / `push` / `checkout` / `restore` / `reset` / `stash` / `clean` / `switch`。只允许只读命令（`status` / `diff` / `log` / `show` / `blame`）。
3. **结论必须可复现、可定位**：每条缺陷要么给出**复现步骤 + 证据文件**，要么给出**`文件:行号` + 触发条件**。二者都没有的，只能标为「推测」，不得写进缺陷清单，另放 `speculation.md`。

> 为什么第 1 条这么严：本项目的**工作区当前不干净**（见第二节实测数字）。你一旦顺手改代码，用户就分不清哪些改动是你的、哪些是开发者未提交的在研工作。**这是本项目最贵的失败模式。**

### 本机 shell 四个坑（先读，省两小时）

1. `git` 在部分工具通道下会报 `error launching git`，改用 PowerShell 或换通道；一次失败不要判定环境坏了。
2. PowerShell 前台调用常**不回显 stdout**：用后台执行再取输出。
3. 定向跑单个测试类必须加 `-Dsurefire.failIfNoSpecifiedTests=false`，否则别的模块「无匹配用例」会让整轮 build 失败。
4. 本机 surefire fork JVM 会启动失败（`forked VM terminated without properly saying goodbye`），必须加 `-DforkCount=0` 在进程内跑 —— **这是环境问题，不是用例失败**，别当缺陷报。

```powershell
# 定向测试模板
Set-Location "D:\dmwprogram\newdazipingtai\newdazi\RuoYi-Vue"
mvn -pl ruoyi-business -am test "-Dtest=Practical*Test" `
  "-Dsurefire.failIfNoSpecifiedTests=false" "-DforkCount=0"
```

## 三、A 线：静态代码审查（读代码找 bug，占比约 40%）

按 `ruoyi-business/controller` 下的 47 个 Controller 与其对应 Service / Mapper 逐个过；前端过 `RuoYi-Vue3/src/views/business/**`、`src/views/student/**`、`src/utils/**`、`src/router/index.js`。**建议按风险维度扫，而不是按目录顺序读到死。**

### A1 事务与并发（本项目最容易出真 bug 的地方，优先）
- [ ] 多表写是否有 `@Transactional`；是否存在**同类自调用导致事务失效**、`private` 方法上加注解、异常被 catch 后事务不回滚（只 catch 未 rethrow / 未 `setRollbackOnly`）。
- [ ] 读后写竞态：`SELECT` 判空再 `INSERT` 的模式有没有唯一索引或 `FOR UPDATE` 当前读兜底。（已发生过的真实故障：`REPEATABLE_READ` 旧快照下并发同状态 no-op upsert 误报「保存失败」——用同样眼光扫其余 upsert / 状态写入点。）
- [ ] 锁顺序与锁范围：学生锁 / 指派锁 / 配置行锁是否可能死锁；`FOR UPDATE` 是否锁了不该锁的一整段范围。
- [ ] 幂等：交卷、重做、批量采用、签到、支付型操作（AI 任务）重复请求是否只生效一次。
- [ ] 前端轮询与后端写并发：30 秒轮询读到的旧响应覆盖新状态（课堂开关误显示关闭就是这一类，检查是否还有同模式的 `res.data` / 顶层字段误读）。

### A2 越权与数据安全（P0 高发区）
- [ ] 每个业务接口有没有 `@PreAuthorize`；**只按前端传来的 `classId` / `studentId` / `deptId` 查询而不校验归属**的 IDOR。
- [ ] 学校 / 部门（`dept_id`）隔离条件是否在每个列表、统计、导出、批量接口都带上了；批量接口是否**逐条**校验所有权。
- [ ] 前端隐藏按钮 ≠ 后端安全：挑 5 个学生账号可访问的页面，直接用学生 token 调教师/教研员接口验证（预期 401/403，**绝不能返回数据**）。
- [ ] SQL 注入：Mapper XML 里的 `${}` 拼接、`like '%${...}%'`、`order by ${}`。
- [ ] 文件：上传后缀/大小/MIME 校验，下载路径拼接是否可 `../` 穿越，相对 `uploadPath` 是否会被 Tomcat 解析到临时目录（本机已踩过一次）。
- [ ] 敏感信息回显：AI Key / 口令 / Token 是否出现在接口响应、日志、异常信息里；`v-html` 的 XSS。
- [ ] **专项**：`SchoolScoreDebugController` 这类调试用 Controller 是否有生产可达入口、是否只靠权限注解保护。

### A3 一致性与口径
- [ ] 成绩 `NULL` 与 `0` 混用（平均分分母、导出、图表三处口径是否一致）；缺分项是否被补零。
- [ ] 统计与明细是否同源（列表人数 vs 图表分母）；时间边界（学期起止、**打字统计的末日时间边界**）是否有 off-by-one。
- [ ] 软删/硬删混用是否留下孤儿数据（答案 → 作业 → 课程 → 班级删除链）。删题归档、按课程归属清理作品的路径重点看。
- [ ] 版本号 / 轮次（`theoryRevision`、`typingRevision`、作品 version、任务 executionToken）在旧页面重提、并发重做时是否真的拒掉。

### A4 资源与外部依赖
- [ ] `InputStream` / POI `Workbook` / `HttpClient` / JDBC / 文件流是否 try-with-resources；LibreOffice 转换是否有进程残留与超时杀进程；大文件是否整块读进内存。
- [ ] 线程池 / 定时任务 / 异步 worker 是否有界、是否会吞异常静默死亡（AI 批改 worker 重点看）。
- [ ] 外部依赖失败时的行为：Judge0、CryptPad、EMQX/MQTT、通义视觉模型超时 → 是有界重试、熔断、降级，还是雪崩 / 无限排队。
- [ ] 配置开关默认值是否安全（如 `iot.mqtt.downlink-enabled=false`、`PRACTICAL_INSIGHT_ENABLED` 默认关闭、`practical-insight.max-cost-yuan` 费用软上限）；**在途调用是否可能绕过费用上限**。

### A5 性能（静态层面）
- [ ] N+1：循环里查库 / 循环里调远程接口。
- [ ] 全表扫：`selectList` 无 where 后在内存过滤；缺索引的联合查询条件；深分页 `limit 100000, 20`；`foreach` 巨型批量。
- [ ] 大响应：一次返回全班/全校明细而不分页、不裁剪字段。
- [ ] 重复计算：同一请求内多次读同一份配置/字典。

### A6 前端与可维护性
- [ ] 组件卸载未清 `timer` / WebSocket / 事件监听造成的内存增长与幽灵请求。
- [ ] 长列表无虚拟化、`v-for` 用 index 作 key 且列表可变。
- [ ] 上传/表单在前端校验但后端不校验；错误提示是 500 白屏还是可读文案。
- [ ] 结构异味：`com.ruoyi.business` 下同时存在 `util` 与 `utils` 两个包（重复工具类的信号）；超长 Service / 复制粘贴分支；魔法数字；`console.log` 残留。

## 四、B 线：动态功能测试（跑起来验证，占比约 35%）

**顺序固定：既有测试套件 → 接口冒烟 → 浏览器冒烟。** 能停在更早一层拿到结论，就不要强上 UI。

1. **先跑既有测试**（最便宜的 bug 探测器）：
   - `mvn -pl ruoyi-business -am test` 全套（带第二节的两个 `-D` 参数），记录失败/错误/跳过数字与每一条失败的**最小复现**。
   - `RuoYi-Vue3`：`npm run test`（或 `package.json` 里实际的测试脚本）。
   - 同时做一次**测试质量审查**：哪些测试只断言「不抛异常」或只测 getter、哪些关键链路（重做、批量采用、删除、越权）根本没有测试 —— 这本身就是高价值发现。
2. **接口冒烟**：用四个角色各自的 token，过登录、首页数据、课程/班级列表、批改列表、成绩汇总、教研员统计、学生任务列表。记录 HTTP 码、业务码、耗时、响应体大小。
3. **浏览器冒烟**（Playwright，产物只写 `output/health-check/<今日>/`）：三角色各进 1～2 个核心页，无白屏、无 `pageerror`、无持续 500。重点走这几条真实链路：
   - 教师建/改课程与题目 → 指派 → 学生答题（选择/判断/打字/操作/流程图/Python）→ 交卷 → 教师批改 → 成绩汇总 → 重做（理论/打字）→ 学生端显示待重做
   - 纸质 PDF 导入 → AI 建议 → 教师核对/批量采用 → 成绩写入 → 学情诊断入口
   - 教师工具网关、协作小组、班级分组与学生桌面
4. **健壮性**：空数据、超长输入、特殊字符、并发双击、断网/依赖超时时的页面表现。
5. 需要写数据时：**只允许新建自己造的、带明确识别前缀的测试数据**，全程记录 SQL，测完清理并复核计数（见第八节）。**不得改动真实学生的成绩、批改结论、作品。**

## 七、D 线：优化建议（与缺陷分开列，占比约 10%）

不要和 bug 混在一张表里。每条给：**现状 → 问题 → 建议 → 预期收益 → 改动成本（S/M/L）→ 风险 → 涉及文件**。分类至少覆盖：

- 性能（慢接口、慢 SQL、可缓存、可批量）
- 可靠性（缺幂等、缺超时、缺补偿、静默失败）
- 可维护性（重复代码、超长类、缺失测试、命名异味、`util` 与 `utils` 之类结构问题）
- 可观测性（该记的日志没记、记了敏感信息、错误码不可诊断）
- 安全加固（默认值、鉴权粒度、上传约束）
- 体验与可读性（错误文案、白屏、加载态、窄屏布局）

**克制原则**：宁报 15 条有分量的，不凑 60 条「建议加注释」。不建议换技术栈、不建议重写核心模块、不建议改核心权限模型 —— 这类属于方案级变更，最多作为一句话方向提及，并注明需用户专门立项。

## 八、红线与「停下来问」清单

**默认执行（无需请示）**：读文件、跑既有测试、构建、本机接口/页面冒烟、只读 `SELECT`、造前缀化测试数据并自行清理、复用 `output/stress` 脚本做低/中并发。

**必须先问用户**：
- 重启或停止**不是你自己启动的**进程（本机 8080/80 有开发中的服务）
- 任何 DDL、`TRUNCATE`、批量 `UPDATE/DELETE`、无法秒级回滚的数据改动
- 调用**会产生真实费用的外部模型**（AI 批改、视觉识别、学情生成）—— 默认**一律不触发**，改为读日志与静态审查
- 连接正式服务器（130 / 跳板 123 / 129 / CryptPad / EMQX / Judge0）做**写**操作；只读探查也要先说明目的再连
- 任何 git 写操作、`scripts/deploy.py deploy|rollback`
- 需要新增依赖或修改 `application*.yml` / `pom.xml` / `package.json` 才能测到

**绝对禁止**：改业务代码或测试代码来「让它通过」；为凑覆盖率写空测试；在报告或日志里回显 `contexts/secrets.local.md` 的任何内容；`--no-verify` 绕过校验；删除或覆盖 `output/` 下别人的既有产物。

## 九、交付物

全部落在 `output/health-check/<YYYYMMDD>/`：

```
README.md            # 总入口（必读）：一句话结论 + P0/P1 清单 + Top10 建议 + 未覆盖说明
scope.md             # 实际覆盖了什么、明确没覆盖什么及原因（诚实比好看重要）
defects.md           # 缺陷清单（BUG-xxx）
optimizations.md     # 优化清单（OPT-xxx）
test-log.md          # 跑过的命令与结果：测试套件通过数、构建、接口冒烟、并发档位数据
data-changes.md      # 写入/清理过的测试数据、SQL、前后计数比对（没有写数据也要写明「无」）
speculation.md       # 证据不足的可疑点（不算缺陷，供后续追查）
evidence/            # 截图、日志片段、接口响应、HAR（按缺陷编号命名，脱敏）
```

`defects.md` 每条字段：

| 字段 | 说明 |
| :--- | :--- |
| 编号 | `BUG-001` 递增 |
| 标题 | 一句话 |
| 级别 | **P0** 数据错误/越权/主流程阻断/安全漏洞；**P1** 主要功能不可用；**P2** 一般缺陷；**P3** 体验细节 |
| 定位 | `文件:行号` **或** 接口路径 + 页面 |
| 复现 | 精确到能照着重跑（含角色、账号、课程/班级 id） |
| 预期 / 实际 | 实际含报错原文（脱敏） |
| 复现概率 | 必现 / 偶发（频率）/ 未复现 |
| 影响面 | 涉及哪些角色、是否影响在用班级与已发布成绩 |
| 修复方向 | 一句话思路，**不要写代码**；提示是否需要同伴的 SQL / 前后端配套 / 重启 |
| 证据 | `evidence/` 下具体文件 |

## 十、汇报节奏与语言

全程用**简体中文**交流（命令本身不必翻译，英文结果用中文解释含义）。每完成一条线（A/B/C/D）用大白话汇报四句：**做了什么 / 成功还是失败 / 有没有问题 / 下一步做什么**。用户不关心实现细节，别贴长日志。

自主推进，不要因为「能不能测 X」反复回来问 —— 除第八节红线外**自己决策并把假设写进 `scope.md`**。

## 十一、收尾：零改码自证（必做，不可口头声明）

1. 再拍一次快照并比对：
   ```bash
   git status --porcelain=v1 > output/health-check/<今日>/final-git-status.txt
   diff output/health-check/<今日>/baseline-git-status.txt output/health-check/<今日>/final-git-status.txt
   git diff --stat        # 与基线一致，且不含你造成的新增
   ```
   预期：**唯一允许的新增**是你自己建的 `output/health-check/<今日>/` 里的文件。基线里那 122 条（含 83 个源码文件）必须**逐字节原样存在**。
2. 若有偏差 → 立即如实说明是哪一个文件、改了什么、如何恢复，**不要偷偷改回去**。
3. 向用户口头汇报（不超过 10 行）：
   1. 发现缺陷 X 个（P0 __ / P1 __ / P2 __ / P3 __），说出最该先修的 3 个分别是什么、影响谁
   2. 优化建议 Y 条，收益最大的 3 条
   3. 既有测试套件与并发结果（数字，不解释过程）
   4. 测试数据是否已清理还原（前后计数一致）
   5. 明确未覆盖的范围（尤其是被禁止触发的付费 AI 调用、未连的正式环境）
   6. 报告路径
   7. 零改码声明：**未修改任何源代码、未提交 git**，并附第 1 步的 diff 结果
4. 顺手产出一段「**建议追加到 `contexts/PROJECT_CORE.md` 的一句话事实**」清单放在 `README.md` 末尾，交给你之外的用户或开发 AI 决定是否录入 —— **你自己不要改 `PROJECT_CORE.md`**。

汇报完成即任务结束。**不要主动提出「要不要我把这些 bug 修了」，那是下一个开发 AI 的工作。**
