# ADR-011：共享主机采用 400 份排队、10 路真实判题

- 状态：已采纳并上线
- 日期：2026-08-23

## 背景

123 平台的 Judge0 异步执行器原为核心线程 2、最大线程 4、队列 500。Java 执行器会在使用完核心线程后优先入队，只有队列填满才尝试扩到最大线程，所以课堂突发提交时实际长期只有 2 路判题。129 是 16 线程、31GiB 的共享扩展机，还承载 CryptPad 与 EMQX，不能把“400 人提交”解释为同时启动 400 个不受控沙箱。

## 备选方案

1. 单机同时运行 400 个沙箱：响应可能更快，但远超 129 的 CPU、内存和进程余量，会拖垮共享服务，否决。
2. 只增加 Java 队列、不增加真实 worker：能减少投递拒绝，但排空时间仍由 2 路判题决定，否决。
3. 400 份提交排队、10～12 路真实判题：快速落库和排队，以受控 worker 消化，并为 CryptPad、EMQX 和宿主机留资源，采纳。

## 决策

123 将 `judge0Executor` 的核心线程、最大线程和队列容量外置；生产为 10/10/1000，课程班级并发门限为 60。129 Judge0 使用 `COUNT=10`、`MAX_QUEUE_SIZE=512`，server 容器限 2 CPU/2GiB，worker 容器限 10 CPU/16GiB。提交先落业务库，再进入进程内执行器；执行线程再把真实用例送入 Judge0 Redis/Resque 队列。容量声明统一为“400 份同时提交可排队，10 路真实判题”。

## 结果与证据

正式环境完成 50/100/200/400 四档平台端到端 `CUSTOM_RUN`：各档接口接收率 100%，无 `SERVICE_BUSY`，终态全部 `ACCEPTED`。400 档接口 P95 约 1012ms，接口接收完成后约 22.2s 排空；压力采样 worker 约 739% CPU、1.236GiB 内存，CryptPad 和 EMQX 同时保持 HTTP 200。报告为 `output/stress/judge0-400-acceptance-20260823_171057.json`。

## 后果与限制

- 单份正式提交若含 6 个测试点，会产生约 6 倍真实 Judge0 作业；排空时间不能直接套用单用例压测数据。
- 本轮用一个受控学生账号并发发出 400 个请求，验证基础设施容量，不等同于 400 个不同账号的真实课堂交互演练。
- Java 执行器队列是进程内队列。独立刷题提交虽先落库，但排空期间重启的恢复能力未在本轮验收，运维应避免在途重启并后续补恢复设计。
- 继续增加 worker 必须重新评估 129 的共享资源，不允许直接把 `COUNT` 提到 400。

## 回滚

123 将核心/最大线程恢复为 2/4、队列恢复 500、课程并发恢复原值后按 stop→等待 stopped→start 重启。129 恢复 `/srv/judge0-python/backups/config-20260823-judge400-v1/` 的 compose 与 `judge0.conf`，只重建 Judge0 server/workers；PostgreSQL、Redis、CryptPad、EMQX 和业务库不做删除。
