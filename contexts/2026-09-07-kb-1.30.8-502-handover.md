## 0. 一句话结论

- **问题不是代码逻辑坏了，而是"单体后端冷重启"造成不可用窗口**：发布/回滚时对后端做了
  `nssm stop → Stop-Process -Name java -Force → nssm start`，这段期间（约 1~2 分钟，含 JVM 启动预热）
  后端不接受请求，nginx 代理到 3009 就返回 **502**；叠加当日学生真实登录量大，表现为"卡 + 接口异常"。
- 用户看到的"在线用户 7660"被误导为"人太多"，其实是**统计口径虚高**（见 §5），不是服务器故障。

## 3. 为什么会 502（根因，最重要）

**根因 = 单体后端冷重启窗口，不是代码 bug。**

- 本平台后端是**单体 Spring Boot**，由 NSSM 服务 `NewDaziBackend3009` 承载。
- 发布/回滚流程采用：`nssm stop`（等 40s）→ 若有 java 残留则 `Stop-Process -Name java -Force`
  → `nssm start` → 探活 3009。**"停止 + 启动 + JVM 预热"这段期间后端完全不可用**。
- 期间 nginx 把 `/prod-api/*` 反代到 `127.0.0.1:3009`，后端未监听/未就绪 → nginx 返回 **502**。

**nginx/后端日志实测证据（唯一性关键）**：
```
2026/09/07 14:18:38 [error] ...connect() failed (10061: No connection could be made because
the target machine actively refused it) while connecting to upstream,
request: "POST /prod-api/login", upstream: "http://127.0.0.1:3009/login"
```
（`10061 active refused`＝后端 3009 那一刻没有进程/未监听；这正是"冷重启中"的典型特征。）

**结论**：502 不是"代码逻辑坏了"，是**后端被冷重启时的那段时间**。14:18:38 那几条 502 与回滚时的重启窗口吻合。

## 4. 诊断过程中还发现的事实（供你参考，避免误导）

- **线上实际运行的是 09-07 的 release**：后端 `20260907_flowchart_ai_fix_v1`、前端 `20260907_flowchart_ai_ui_v2`；
  而 `contexts/PROJECT_CORE.md` 此前只记到 **1.30.5**，**上下文版本落后于线上**。线上 `biz_platform_update` 最大是
  `update_id=87 / 1.30.7`（09-07 画程 AI 修复）。**发布/排查前务必以线上真实状态为准，别信上下文版本号。**
- **"在线用户 7660"的算法**：`/monitor/online` 和诊断中心"在线用户"都取自 **Redis 里 `login_tokens:*` 的 key 数量**
  （`SysUserOnlineController.list()` 用 `redisCache.keys(LOGIN_TOKEN_KEY + "*")` 遍历）。`TokenService` 里
  `createToken` 每次登录都 `UUID` 生成**新 token**存入 Redis，TTL=`token.expireTime`（配置为 **120 分钟**），
  且**旧 token 不会因再次登录被删除**（只有显式退出才 `delLoginUser`）。
  → 所以"在线"= **"最近约 2 小时内成功登录生成的 token 累积数"**，不是真实同时在线人数。
  **学生普遍直接关浏览器、不点退出**，token 会一直挂满 120 分钟，因而累积虚高。**这不是故障，是统计口径问题。**
- **当天登录量大是真实的**：`sys_logininfor` 表今天(2026-09-07) 共 12,152 条、去重账号 2287、去重 IP 58；
  13:00 后 10,425 条、去重 IP 仅 34。**机房学生共用一个交换机/NAT，所以"很多学生显示同一内网 IP"是正常的**
  → 不能据此误判为"单机脚本刷登录"。这是真实学生并发登录。
- 13:00 起的登录量高峰 **早于我 13:49 的发布**，所以登录洪峰本身与我的改动无关。

## 6. 给新 AI 的红线 / 正确做法（避免再 502）

1. **绝不在师生密集时段对单体后端做"停止→强杀→启动"的冷重启**。这是本次 502 的直接原因。
   若确需发布后端：选**低峰窗口**（如晚上/凌晨）并提前告知；或采用**无感/滚动**方式（若未来支持多实例）；
   实在必须重启时，向用户明确"会有 1~2 分钟 502"。
2. **发布前先核对线上真实状态**（NSSM AppDirectory、nginx root、`biz_platform_update` 最大版本），
   不要依赖 `PROJECT_CORE.md` 里的版本号——它可能落后。
3. **新发布目录必须复制外置 `config/`**（否则后端用包内默认配置，3009 不监听）。
4. **nginx.conf 改 root 用「无 BOM UTF-8」写入**；改完必须 `nginx -t`，再**重启 `UnifiedNginx` 服务**
   （本机 `nginx -s reload` 会被拒绝 Access denied）；备份 nginx.conf 到 `backups/…/nginx.conf.before`。
5. **不要整仓打包上线**：当前工作区包含大量**未收口**改动（在线协作工作台 `CollaborationWorkspaceService`、
   `collab_workspace_v2.sql`（未迁移）、流程图 AI 等）。要上线这两处修复，应**只挑最小改动**做成干净包，
   并确认不引入未验证代码。
6. 更改业务行为（如课堂表现原因可留空）属**行为变更**：上线后要向用户说明，并同步 `RELEASE_LOG.md`、
   `biz_platform_update`（本次已写 `1.30.8`/update_id=88，但**随后已回滚**，如交付请注明"已回滚/未生效"）。
